## Theme

**One theme:** give the operator the same authority over rules and
spam decisions from the browser that SP6c gave from the CLI.

The classifier is trustworthy (UAT confirmed the buckets fire
correctly and the Junk move sticks). What the operator does NOT have
today is a way to **react** to a misclassification without SSHing to
production and running `psql -c "UPDATE mail_sentinel_rule …"`.
SP6d closes that.

## In scope

### A. Rules CRUD in UI with mandatory Propose / Apply

**Operator-facing UI:**

- Rules tab gains a "New rule" button (top-right of the table) and
  each row's Edit affordance opens the same editor.
- Form fields (all editable):
  - `name` (unique slug, kebab-case, validated client-side)
  - `description` (freeform, one line, ≤120 chars)
  - `priority` (integer 1–100, numeric input with hint "lower runs
    first" — matches the header hint already shipped in SP6c H)
  - `enabled` (toggle)
  - `condition` (Monaco JSON editor, schema-validated on blur —
    reuse the schema `rules_store.create` enforces today)
  - `actions` (multi-select checkbox: `archive`, `mark_read`,
    `label:<slug>` with text input, `notify:<channel>` with text
    input; the two label/notify variants can be added multiple
    times)

**Propose / Apply flow (mandatory, per operator directive):**

- Submit does NOT PATCH the rule directly. It first POSTs to a new
  endpoint `POST /mail-sentinel/rules/propose`:

  ```json
  {
    "name": "…",
    "priority": …,
    "enabled": true,
    "condition": {…},
    "actions": [ … ],
    "window": {"kind": "recent", "count": 200}
  }
  ```

- The proposal endpoint:
  1. Validates the rule against the existing store validator
     (raises `RuleValidationError` on schema breach — 422 to the
     UI).
  2. Loads the last `window.count` (default 200, max 2000) rows
     from `mail_sentinel_spam_decision` in reverse-chronological
     order.
  3. For each historical decision, replays the rule against the
     captured envelope (sender, subject, headers snapshot — see
     schema note below) and computes `would_match: bool`.
  4. Loads every currently-enabled rule with `priority <` new
     rule's priority. If any earlier-priority rule would ALSO have
     matched, records `would_shadow: [rule_name, …]`.
  5. Returns:
     ```json
     {
       "valid": true,
       "matched_count": 17,
       "would_shadow_count": 3,
       "matched_examples": [
         {"decision_id": "...", "sender": "...", "subject": "...",
          "current_bucket": "spam", "would_shadow_by": null},
         ...  // up to 10
       ],
       "would_shadow": ["newsletter_unsub", "vip_ceo"]
     }
     ```

- The UI renders:
  - A summary bar: `17 matches / 200 historical decisions · 3
    shadowed by newsletter_unsub, vip_ceo`.
  - A table of matched examples with per-row current bucket + a
    warning icon when shadowed by an earlier rule.
  - An **Apply** button, only enabled once the operator explicitly
    ticks "I have reviewed the matches" (guardrail against
    Apply-without-look).

- Apply commits via the existing `POST /mail-sentinel/rules` (for
  new rules) or `PATCH /mail-sentinel/rules/{id}` (for edits).
  No new mutation endpoint.

**Schema note:** the current `mail_sentinel_spam_decision` schema
captures `sender_email`, `subject`, `received_at`, but not the raw
headers. The Propose step's rule replay is therefore limited to
`from_contains`, `subject_contains`, and `header_matches` against a
minimal synthetic header set. Rules using `header_matches` on
`List-Unsubscribe`, `List-Id`, etc. will show `matched_count = 0`
in the simulation UNTIL the SP6d migration below lands the
`envelope_headers JSONB` column and the adapter captures headers at
decision time. This is a known limitation; the summary bar prints
"Simulation partial: header rules not evaluated" when detected.

**Delete flow:** unchanged (already ships in SP6c). No propose step
for delete — deletion is reversible via CLI.

### B. Origin mailbox column on Recent Spam tab

- **Schema:** `sql/013_add_spam_decision_provenance.sh` — idempotent:

  ```sql
  ALTER TABLE mail_sentinel_spam_decision
      ADD COLUMN IF NOT EXISTS origin_mailbox_id TEXT,
      ADD COLUMN IF NOT EXISTS origin_mailbox_role TEXT,
      ADD COLUMN IF NOT EXISTS envelope_headers JSONB;
  ```

  Historical rows keep NULLs; the new column is populated
  forward-only.

- **Adapter:** in `src/twaky/sentinels/mail/nodes.py::_terminate`,
  before the atomic Junk move:
  - Read the current mailboxIds via `ctx.mail.get_email(email_id)`.
  - Resolve the role of the first non-Junk mailbox via
    `ctx.mail.resolve_role_mailbox_id` (already ships in SP6c —
    invert the resolver to give role from id via a new helper or
    a single `Mailbox/get` batch).
  - Pass both values into `record_spam_decision(...)`.
  - Also capture a header subset (`from`, `to`, `subject`,
    `list-unsubscribe`, `list-id`, `authentication-results`) into
    the new `envelope_headers` JSONB column so the Propose step's
    simulation can evaluate `header_matches` rules against
    historical decisions.

- **API:** `GET /mail-sentinel/spam/recent` row shape gains
  `origin_mailbox_role` and `origin_mailbox_id`. Backward-compat via
  `?with_provenance=1` query flag during rollout; default OFF for one
  release, then flipped to ON.

- **UI:** Recent Spam tab table gets a new column between "Received"
  and "Signal":
  - Header: "Origin".
  - Cell: the resolved role in a subdued badge (`inbox`,
    `newsletter`, `archive`), OR a truncated UUID + tooltip when the
    role is unresolved, OR "—" for pre-migration rows.

## Non-goals

- Visual condition builder — JSON editor + inline schema validation
  is enough for the target audience (operators comfortable with
  rules-as-code).
- Cross-owner rule sharing / multi-tenancy — rules stay
  per-daemon-owner via the existing owner filter.
- Backfill of `origin_mailbox_id` / `envelope_headers` for pre-SP6d
  decisions. New column starts NULL. The Recent Spam UI shows "—"
  for the historical rows and the Propose simulation degrades to
  "header rules not evaluated" when the sample window includes
  them.

## Success criteria

1. Operator can create a new rule from the UI without hitting a
   terminal. The Propose step returns within 500ms for the default
   200-decision window and 3s for the 2000-decision maximum.
2. Operator can edit or disable an existing rule from the UI, with
   the same Propose gating for enable-with-changes.
3. Recent Spam tab shows the origin mailbox role for every decision
   written after the SP6d migration lands.
4. The Propose step's simulation table surfaces at least one real
   shadowing case that a naive operator would have missed (validated
   via a dogfood run against the primary owner's 200 latest
   decisions).
5. Full test suite green, including tests for the new
   `/mail-sentinel/rules/propose` endpoint and the schema migration.

## Risks

- **Migration on prod requires a `docker exec`** on `twaky-pg` —
  the ADD COLUMN IF NOT EXISTS statements are idempotent and non-
  blocking (no default rewrite), so the risk is procedural, not
  technical. The SP6d plan will explicitly call this out as an
  operator-supervised step; the /goal-autonomous flow cannot run
  it.
- **Simulation false negatives** — historical decisions that
  pre-date the `envelope_headers` capture will not evaluate
  `header_matches`. Mitigation: the summary bar prints the caveat;
  operators know to widen the sample window (up to 2000) once the
  capture has been running for a week.
- **Propose latency** — replaying rules over 2000 decisions is
  Python-side and O(rules × decisions). For the SP6d scale
  (~single-digit rules), this stays under 3s. If SP6f introduces
  hundreds of rules per owner, the Propose step will need to be
  moved to Postgres (rule condition compiled to a WHERE clause).
  Not a concern today.

## Open questions

- Should Apply be blocked when `would_shadow_count > 0`, or just
  warned? Current design: warned, not blocked. Operator override
  matches the "sharpest lever" framing from the SP6c ADR — we
  never take the lever away from the operator, we surface the
  consequences.
- Does the Propose endpoint need pagination for the matched
  examples? Current design: hard cap at 10 examples, with
  `matched_count` giving the full number. If operators consistently
  ask "show me the other 7", raise the cap; do not build
  pagination yet.

## Plan hand-off

SP6d is intentionally sized to fit one implementation plan:

- Task 1: schema migration + adapter capture + spam_decisions
  store fields.
- Task 2: `POST /mail-sentinel/rules/propose` endpoint + tests.
- Task 3: UI Rules editor (new + edit) with the Propose/Apply
  flow.
- Task 4: UI Recent Spam Origin column + API field surfacing.
- Task 5: docs update (README, rules-cookbook), ADR for the
  simulation-mandatory decision.

Estimated: 3-5 subagent-driven tasks, roughly one overnight
polish loop.
